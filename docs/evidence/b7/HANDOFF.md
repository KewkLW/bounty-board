# b7 HANDOFF: orchestrator presence, registered by name, online from its pid

## What changed
- `lib/proc.js` (new): `procStat` (moved out of `lib/agents.js`, now also returns `comm`) and `sameProcess(pid, start_time)`. It needs only `fs`, so the hub and the CLI can use it without loading the DB.
- `lib/orchestrator.js` (new, `board.presence`): `register({pid, name})`, `status()`, `startupCheck()`. `run/orchestrator.json` keeps `{name, pid, start_time, since, last_seen}` after the process is gone. `status()` re-checks `online` from pid + start time on every call. It returns `{name, expected_name, online, pid, since, last_seen}` plus `start_time, registered, required, pending, warning`. A state change (registered, online/offline, new pid) emits `changed('orchestrator')`, adds a board event when the orchestrator goes offline, and runs the listeners (the registry rewrite).
- `lib/agents.js`: registering a `kind: orchestrator` entry drops every other orchestrator entry from the manifest without signalling it, then calls `presence.recorded()`. Both routes (`bounty orchestrator register` and `bounty agents register --kind orchestrator`) replace the old entry the same way.
- `lib/config.js`: `orchestrator` is normalized to the expected name or null. `require_orchestrator` is a boolean.
- `lib/api.js`: `GET /api/orchestrator`, `POST /api/orchestrator {pid, name}` (403 for worker slots). `/api/state` and `/api/live` carry `orchestrator`. In `/api/live` it is added outside the 2 s snapshot cache, so it is re-checked on every read. `bounty live` text shows it too.
- `lib/registry.js`: the entry has `presence` (the same object) and `board_dir`. `update()` patches the entry, but only from the process that wrote it. `list()` re-checks `presence.online` from pid + start time (`livePresence`).
- `server.js`: puts presence in the registry entry at start and rewrites it on change. `startupCheck()` logs `[orchestrator] WARNING: ...` when bounties are ready/in_progress/blocked and no live orchestrator exists. A timer (watchdog `check_seconds`) catches transitions later.
- `bin/bounty`: `bounty orchestrator [--json]` and `bounty orchestrator register [--name N] [--pid P]`. The default pid is the first ancestor of the CLI that is not a shell (or a `*-bounty` wrapper), and the output names the process it picked. The default name is `$AGENT_NAME`, else board.json `orchestrator`. Workers are refused. `bounty status` prints the orchestrator line.
- `hub/server.js`: each board view has `orchestrator`. The source is the board's `/api/state` when the board is up, else the registry `presence` (re-checked), else only the expected name. `alarm` = required (board or hub config) and work waiting with no live orchestrator. `spawn_orchestrator` is an argv array: no shell, placeholders `{board} {project} {port} {name} {board_dir}`, started detached and not waited on. It is called from `POST /api/orchestrator/start {port}`, which needs `X-Hub-Request`; 404 not configured or unknown port, 409 already online. `/api/hub` reports whether spawning is configured. `/api/reply` answers with `orchestrator: {name, online, ...}`. `{orchestrator}` in on_reply is the registered name, else the expected one.
- `hub/public/hub.js`, `hub.css`: an orchestrator line on every card and project tab. It has a green dot plus "online since" or a grey dot plus "offline since", or "No orchestrator ever registered (expected X)". It turns red with the warning text when `alarm`. **Start orchestrator** shows only when the orchestrator is offline and spawning is configured. A reply sent while it is offline shows "Saved on the board. X is offline, so nobody is reading it live yet."
- README "Orchestrator" section (and the hub/on_reply notes), `config/*.example.json` keys, `skill/totally-not-a-kanban/SKILL.md` section 0: register yourself first in every orchestrator session.

## Decisions to review
- `since`: while online it is when the orchestrator registered. Once offline it is when it was last seen alive (`last_seen`, persisted at most every 15 s while online, and at every read).
- The registry key is `presence`, not `orchestrator`. The existing `orchestrator` string (expected name, used by on_reply and by already running boards) keeps its meaning.
- Red covers both "never registered" and "registered but offline", when work is waiting and `require_orchestrator` is set (board.json, or hub.json for every board).
- The startup warning is a console line, which reaches the journal under systemd. The same text is in `warning` on the API, in `bounty status` and on the hub.

## Tests (`npm ci && npm test`: 70 pass, 0 fail)
- `test/orchestrator.test.js` (real child processes): register via CLI, online, with the same object in `/api/orchestrator`, `/api/state`, `/api/live` and the registry entry. SIGKILL makes it offline on the next read, the registry entry is rewritten, and a board event is added. Pid reuse: a rewritten start time means offline on the board and in `registry.livePresence`. Replacement: the old orchestrator runs on with no signal (its TERM trap file stays absent), the manifest has one orchestrator, and both register routes behave the same. Default pid: a node "agent" runs the CLI through `bash -c "bash -c ..."`, and the agent's pid is registered (not a shell) with the name from `$AGENT_NAME`. Without a name, board.json `orchestrator` is used. Workers get 403 and the CLI refuses them. Startup warning on restart with a ready bounty; `required` is reported.
- `test/hub.orchestrator.test.js`: hub states (online, offline + required = alarm, never registered, a stopped board with the registry presence re-checked from the pid, a wrong start time = offline, hub-wide `require_orchestrator`). Spawn hook argv with every placeholder and shell metacharacters passed verbatim; 403/404/400/409/500. A reply while offline is saved and the answer says offline. A headless Chromium run checks the green/grey/red dots by computed color, the texts, the Start button (click, hook argv, message, stays on the tab), the reply-while-offline text, no button without config, and 390 px with no sideways scroll.
- `test/hub.test.js`: a real board end to end through the hub: no orchestrator, then online, then offline after the process is killed.
